## Status

Begun 2026-11-15 on the user's request ("the ROMs are there": `~/.mimic/roms/kc85/`, KCemu's ROM set: CAOS 2.2 (HC900), 3.1, 4.2, 4.4, BASIC, the D004's floppy ROMs, module ROMs M006/M012/M026/M027/M033 and more). No questions asked at the start; these choices are Claude's, not the user's: all four models (KC85/2, /3, /4, /5; the phase named /3 and /5) since the ROMs are there and the /4 is the /5's base; default model "4"; the D004 floppy unit left out; cassette playback first, saving later.

**The gate is met (2026-11-15):** `tests/tests/kc85_boot.rs` (ignored, real ROMs): KC85/2, /3, /4 and /5 boot to the CAOS menu; a BASIC program typed through the keyboard's pulses runs on the /3, /4 and /5; LOAD reads a three-block KCC program from the cassette on all four models and starts it.

Built:
- `chips-zilog` (new crate): Z80 CTC (timer and counter mode, prescaler, trigger start, a running channel takes a new constant at zero), Z80 PIO (modes 0 to 3, strobe and bit-mode interrupts), the interrupt daisy chain (`Chain`: request, in service, RETI). The machine sees the RETI by looking at the bytes at PC before the instruction (`ED 4D`); `cpu-z80` is unchanged.
- `machine-kc85`: memory switching by PIO A/B and ports `$84`/`$86` (RAM0, RAM4, RAM8 blocks, IRM planes, CAOS C and E, BASIC, the /5's USER ROM segments), the IRM picture line by line (the /2's and /3's spread addresses with a colour byte per 8 × 4 pixels, the /4's column layout with a colour byte per 8 × 1 and the four-colour mode), blink through CTC 2, two sound channels through CTC 0 and 1 with PIO B's volume, the keyboard's pulse protocol (timed by CAOS with CTC 3), cassette playback (KC-TAP and KCC; a strobe at PIO A per zero crossing), two module slots (`slot8`, `slotc`: M022, M011, M006, M012, M026, M027, M033), a stub ROM, savestates, `typed_keys` (paste and `type`), a host keymap.
- Read from the user's ROMs (CAOS 4.2 and 3.1 disassembled with the test file's `disassemble` tool, nothing taken from another emulator): the keyboard's pauses and key numbers (interrupt routines `$E339`/`$E345`, key table KTAB), the tape's half-wave lengths and the lead the load routine needs (`$E56B`, `$E58E`), the inverted volume bits (`$F92E`).
- Tried by hand (headless): M026 Forth on the /4 (`SWITCH 8 C1`, FORTH appears in the menu); M006 on the /2 (`JUMP C` starts the module's own HC901 CAOS with BASIC).

Findings:
- CAOS 3.1 takes six seconds to its menu (it clears memory and prints the screen clear), CAOS 4.x two. The KC85/3's menu shows an empty `%` line behind REBASIC: the BASIC ROM holds the bytes `7F 7F 00` at `$D9C4` (constants), which the menu takes for a word.
- The PIO's output register must be loaded before the port becomes an output: the lines switch the memory the moment the mode is set.
- CAOS 3.1's keyboard routine has no limits on the pauses: a key that starts less than 20.6 ms after the last word is read as part of it. The emitter here keeps 25 ms of silence between keys (whether the real U807 does is not checked).
- Typing is blind (see the debugger notes): BASIC's start takes longer than the pause behind ENTER, so text sent right behind `BASIC` loses its first line.

Not checked against hardware or documents, taken from memory of the system manuals: the colour values, the picture's timing inside a line (the picture is drawn at each line's end; nothing is delayed against the CPU), the PIO's lines while it is an input after RESET (all high), the priority of modules against each other, the KC85/5's RAM8 block numbers, the M011's block rotation and the M033's segment bit. The frame is 312 lines of 112 (KC85/2, /3) or 113.5 clocks.

**D004 floppy unit (2026-11-19, on the user's request "ja, bau den D004"):** `--option d004=on` with ROM role `d004` (KCemu's `floppy20.rom`, D004 ROM 2.0, CRC 4F3494F1). Built:
- `machine-kc85::d004`: the unit's U880 at 4 MHz with 64 KB RAM, the Koppel-RAM (its `$FC00–$FFFF`; the KC reaches it through ports `$F0–$F3`, the upper port byte the address within the page), the KC's control port `$F4` (bit 0 run, bit 1 clear the RAM and hold RESET, bit 2 hold RESET, bit 3 NMI), a CTC at `$FC–$FF` (channels chained), the U8272 with two 5.25" drives (`drive 0`, `drive 1`; select and motor port `$F6`, TC `$F8`, status `$F4`: /DRQ, /INT, ready, index). The unit runs in step with the KC (after every KC instruction the same time at 4 MHz); it is its own debug target `d004` with memory space `d004`, and in the chip list (`d004`: select, status, FDC MSR, PCN, CTC).
- `machine-kc85::modules`: slot `$FC` with the D004's ROM (structure byte `$A7`, control bit 0 on, bit 2 connects Koppel-RAM and `$F4`, bit 5 `$E000` instead of `$C000`); savestates of older versions (no slot `$FC`) still load.
- `chips-amstrad::fdc`: an 8 MHz clock (`Fdc::new_8mhz`, step rate in 1 ms units), DMA mode (SPECIFY ND = 0: no RQM in the execution phase, `drq()`), the INT output (`int()`), TC (`terminal_count()`: normal termination after the current sector), the index pulse. The CPC uses none of it and is unchanged (its disc tests pass). A seek's INT is cleared by the next command: the D004's boot loader recalibrates a drive already at track 0 and then reads without SENSE INTERRUPT STATUS; with the INT left standing its read loop stopped at once.
- `drives-other::cpc_drive`: `CpcDrive::kc85()` with 80 cylinders and raw MicroDOS dumps (`.img`: 80 tracks, 2 sides; 5 × 1024, 9 × 512 or 16 × 256 bytes, records from 1), written back raw; `media::dsk::{RawGeometry, Dsk::from_raw, Dsk::to_raw}`.
- Read from the user's D004 ROM 2.0 (disassembled with a scratch tool over `cpu-z80`'s disassembler): `JUMP FC` enters at `$F012` → `$E003`; the KC clears the D004, copies the boot loader (ROM `$F260`) into the Koppel-RAM, releases RESET and waits for the status at `$FFB3` (1: system found, 2–5: errors). The loader: motor on (`$F6` = `$21`), wait for READY, SPECIFY `9F 14` (DMA), RECALIBRATE, READ DATA track 0 record 1 (N = 3) into `$9000`, 512 bytes by DACK, then TC; "SY" at `$9000` and "S" at `$9002` mean a system, started at `$9004`.
- Tests: `machine-kc85` `the_d004_boots_from_the_koppel_ram_and_reads_a_sector_by_dma` (no user ROMs: a KC program loads a D004 program into the Koppel-RAM; RAM clearing, the NOPs up to `$FC00`, DMA read with TC, result bytes, debug target, savestate); `kc85_boot` `jump_fc_boots_the_d004_from_disc` (ignored, real ROMs: `JUMP FC` on the KC85/3, /4 and /5 reads a self-made boot sector from drive 0 and runs it, after 110 / 80 / 80 fields).
- Speed: KC85/4 without the D004 unchanged (3000 fields in 1.1 s); with it held in RESET 1.5 s, running 2.6 s (23 times real time).

Not checked (D004): taken from MAME's `bus/kc/d004.cpp` (BSD-3-Clause, read as a description, no code taken) and not seen in a document: the `$F4` bits of the KC side, the RAM clearing of bit 1 (the real circuit may instead keep the data bus at zero until `$FC00`), the select port, the CTC at `$FC`; the polarity of `$F4`'s bits on the D004 side is read from the ROM (the loader waits while bit 7 is high and stops when bit 6 goes low), the index bit's polarity is a guess. RESET resets the FDC and the CTC here. The KC's RESET does not reach the D004 (the manual: RESET returns to the PC mode without stopping MicroDOS); POWER resets it. The D004's own two module slots (`$F0`, `$F4`), drives 2 and 3, the GIDE versions of the ROM (`floppy30`–`floppy32`, ML-Soft) and the KC's wait states on Koppel-RAM accesses are not built.

## BASIC tapes and fast paste (2026-11-20)

On the user's report ("lädt nicht sauber von tap", "copy/paste im BASIC-Editor zu langsam"; test tape: the user's `steinschlag.tap`, a CSAVE file of 17 blocks).

- **The tape.** `CLOAD"STEIN"` read every block without an error and the program was in memory byte for byte, but the keyboard was dead afterwards. Read from the BASIC ROM: after CLOAD (`$DC43`) the input stays on the tape, and the prompt's input loop (`$C5AE`) reads its characters from there until a `$03` comes (`$DF27`: BRK, which closes the files). CSAVE's close call (`$DD5C`, `LD DE,$0343`) hands CAOS that `$03` as its data byte, so on a tape a KC wrote it stands right behind the program. The image holds zeros there (made by a tool); BASIC used up the block and CAOS' driver (`$C819` in the C ROM) waited for another block for ever. `tape::mend_basic` now gives a CSAVE file (`$D3` or `$D7` three times) without any `$03` behind its program that mark when the tape goes in: behind the last byte that is not zero (text a tape carries there to start the program stays), in a new last block where there is no room. Machine programs and files that have the mark are not touched. Steinschlag loads and runs on the KC85/3, /4 and /5.
- **Keys while loading spoil the block; that is CAOS, not the emulation.** The tape's timing is right with keyboard pulses in between (counter values `$90`/`$78`/`$4A` throughout), but the keyboard's interrupt routine writes the key code to `(IX+13)` (`$E3B5`, and 0 at the timeout, `$E33F`), the cell the load routine keeps the block's checksum in (`$E599`, `$E5D1`). After the error CAOS waits for the same block again, which a tape image never repeats (rewind and load again). Nothing changed here.
- **Paste.** `Machine::paste_chars` for the KC85: CAOS has no keyboard buffer but one key cell (`(IX+13)` the code, bit 0 of `(IX+8)` "a key is there", cleared by KBD; the same in HC900, 3.1, 4.2 and 4.4). One character goes in per field while the bit is clear; none while PIO A's interrupt is on (CAOS reads the tape); without CAOS' cells (IX not `$01F0`, I not 1, RAM0 off: the stub ROM) the keys type as before. 776 characters in 896 fields on the KC85/4 and /5, 1105 on the /3 (typed: about 135 ms a character and a second per line, some 6300 fields); the desktop runs the paste at warp.
- Tests: `machine-kc85` `a_basic_program_gets_the_end_mark_csave_writes`, `pasted_text_goes_into_caos_key_cell_one_character_at_a_time`; `kc85_boot` (real ROMs) `cload_reads_a_basic_program_and_gives_the_keyboard_back` (/3, /4, /5: a tool-made CSAVE tape, then RUN), `pasted_text_reaches_basic_faster_than_typed` (all four models); the tool `tape_tool` for a tape of the user's.
- **Doubled letters typed fast (same day).** On the user's report that typing loses characters ("HALLO" gave "HALO"). The emitter (`keyboard.rs`) sends a word of 53 ms and repeats it while the key is held; a key let go and pressed again before the word's end went on as "held", and CAOS, which takes a key for new only after 20.6 ms of silence, dropped the second letter. The emitter now keeps the 25 ms of silence before the word of a key pressed anew that equals the word sent last, and it remembers a key pressed and released while another word was on the way and sends it once (two more bytes in the savestate: older KC85 states do not load). The input mapper keeps shortest key times for every machine besides (`docs/claude/devices.md`). Tests: `machine-kc85` `a_key_pressed_again_during_its_word_is_sent_after_the_silence`, `a_key_pressed_and_released_during_another_word_is_sent_once`; `kc85_boot` `a_doubled_letter_typed_fast_counts_twice` (all four models, four timings).
- Not done: a tape that repeats or waits after a read error; KBD is limited to one pasted character a field (CAOS could take more).

## Z80 timing (2026-11-19)

On the user's request the KC85 and the D004 run their Z80 with `step_timed` (before: `step`, the rest of the machine caught up after each instruction). The rest catches up before each access that can see it (I/O, interrupt acknowledge, writes to $8000–$BFFF; the D004 before its I/O), not before every access: that cost a third of the speed. Measured (3000 fields, KC85/4, best of 4, interleaved): 1.07 → 1.15 s without the D004, 2.91 → 3.11 s with ML-DOS on the D004 (+7–8 %). All unit tests and the ROM tests (`kc85_boot`: boot, BASIC, tape, `JUMP FC`) unchanged, the boot sector after the same fields (110/80/80); ML-DOS still boots to its prompt.
