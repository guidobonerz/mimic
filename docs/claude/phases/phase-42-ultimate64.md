## Status

2026-11-23: added on the user's request ("add new machine ultimate64 … add a function to test alternative machine cores different from the ultimate core"), narrowed by the user the same day to "emuliere erstmal nur den ultimate64 und commodore 64u". Built the same day:

- **Machine `ultimate64`** (`machine_c64::ultimate64_entry`, `C64::new_ultimate`), models `u64` (default; Ultimate 64 and Elite) and `c64u` (Commodore 64 Ultimate, Elite II board). It is the C64 of `machine-c64` with a board setting; every C64 option still applies. `uci` is on unless switched off.
- **Turbo CPU** (`machine-c64::turbo`, `C64::turbo_cycles`): options `turbo=off|manual|registers|enablebit`, `cpu_speed=<MHz>` (the board's table), `badlines=on|off`; the registers `$D030`, `$D031`, `$D07A`, `$D07B`; chip "turbo" in the debugger's chip list; in the savestate (chunk `U64T`). The extra CPU cycles of a VIC-II cycle reach only memory inside the FPGA (RAM, KERNAL, BASIC, character ROM); an access to I/O or a cartridge waits for the next 1 MHz cycle. Breakpoints stop between turbo cycles.
- Frontends: ROMs from the `c64` folder, the C64's keymap, joystick port and monitor profile.

Checked: 8 unit tests (`tests_ultimate64.rs`: models, option errors, turbo off = a C64 cycle for cycle, cycle counts at 4 and 16 MHz, external accesses at bus speed, registers, breakpoints, savestate). With the real ROMs a BASIC loop `FOR I=1 TO 3000:NEXT` takes 189 jiffies on the C64, 23 at 8 MHz and 6 at 64 MHz without bad lines. A C64 frame costs the same as before (3000 frames: 21.3–21.8 s for both `c64` and `ultimate64` without turbo; 76 s at 48 MHz).

2026-11-23, later the same day, on the user's request ("baue das menu. der ultimate emulator soll soweit gehen, das ich das flashen von firmware testen kann"): **the menu and the firmware updater** (`machine-c64::u64menu`).

- Panel control 5 "MENU" is the multi button (a brief press). The menu freezes the C64 (the CPU stands still, the chips run on), takes the keyboard and is drawn 40 × 25 characters over the picture with `mimic-core::font`; a reset closes it; it is in the savestate (chunk `U64M`).
- Browser over the frontend's file area (`~/.mimic/ultimate` with its mounted folders): folders, context menu by extension (disk images "Run Disk"/"Mount Disk", PRG "Run"/"Load", CRT "Run Cart", update files "Run Update"). F5 tools (Reset C64, Reboot C64, Remove Disk from Drive A, System Information), F2 configuration ("U64 Specific Settings": Turbo Control, CPU Speed, Badline Timing; the settings are now in the savestate, `U64T` version 2), F3 keys.
- Updater: checks the file (extension `u64` on the u64, `ue2` on the c64u; not empty; at most 64 MB), erases, programs and verifies in steps of 32 KB a frame, then asks for a key and restarts the machine. The flash is the file `Flash/.firmware` of the file area in a format of this project (name, length, CRC-32, the bytes). A power cut (POWER, or closing the emulator) while it writes leaves a damaged flash: the board then shows "NO VALID FIRMWARE" at every power-on until the file is deleted. System Information shows what is installed.
- What this does not do: nothing of an update file is run or understood. The layout of the real update files is not documented and the firmware's sources are GPL (golden rule 7), so the updater proves the procedure, not that a firmware works.

Checked: 6 more unit tests (14 for the machine, 79 in the crate, all pass): freeze and picture, browser with PRG/disk/eject, configuration and savestate, a complete update with its CRC, refused files, a power cut and the recovery. By hand with the real ROMs through the debug server (`panel MENU tap`, `input key`): browser, a 3 MB update to "Update complete", restart, System Information with the installed file.

2026-11-23, third step: the user pointed to real update files ("hier liegen verschiedene firmwares: c:\Users\guido\applications\mimic\ufirmware": `update_v3.15a.u64`, `.ue2`, `.cfw`, `.u2p`, `.u2l`, `.u2r`). Looked at as data (first bytes, texts; nothing disassembled), they gave:

- **The layout**: `.u64`, `.ue2`, `.u2p`, `.u2l` start with three little-endian words: load address `$03000000`, the image's length (file length − 12) and the start address inside the image; the image is an uncompressed program (the updater itself, with the FPGA bitstream, the application and the ROM files inside). `.cfw` has 36 bytes in front (`DE AD 15 41`, then the product name "U64MK2" zero-padded to 32 bytes) and is otherwise the `.ue2` file byte for byte. `.u2r` has no header (not used here).
- **The version text** ("3.15a") stands in front of the title's format `%s (V1.%b) %s`.
- **Texts**: the updater's title lines, "Invalid Update Image", "Update for Wrong Product", "About to update. Continue?", "Not flashing.", "Done!", "Turning OFF machine in 5 seconds....", the help page, several menu entries.

Built from it: the updater checks the header (and a `.cfw`'s product), finds the version, asks "About to update. Continue?" before it writes, and shows the real messages; the c64u takes `.ue2` and `.cfw` (the earlier guess `ue2` for the Commodore 64 Ultimate is replaced: its file is `.cfw`, product "U64MK2") and switches off and on again five seconds after "Done!", the u64 waits for a key; the installed version is in the menu's title and in System Information; flash file format `MIMICFW2` with the version. Tests: 16 for the machine, 81 in the crate, all pass (before: 14 and 79; two new: the answer "no", the Commodore 64 Ultimate's files). By hand with the user's files through the debug server: `update_v3.15a.u64` on the u64 (version 3.15a found, flashed, title "Ultimate 64 3.15a", then the `.cfw` refused as "Update for Wrong Product") and `update_v3.15a.cfw` on the c64u (flashed, switched off and on, CRC-32 9DE4973D as the file's).

Still not done by the updater: the real one is the program in the file; it checks its FPGA and application images by their own checksums, writes them and the ROM and HTML files to different places of the flash and asks whether to reset the configuration. The embedded images' places and checksums were not worked out (it would need the program's code).

2026-11-23, fourth step: **the firmware's sources may be read for facts.** The user first exempted the Ultimate sources from golden rule 7, took that back, and then chose the general wording offered ("Allgemein: Fakten ja, Code nein"): sources under the GPL may be read for facts, code is never taken over; rule 7 in `CLAUDE.md` says so now. Read at commit 40188c7 of github.com/GideonZ/1541ultimate: `software/filetypes/filetype_u2p.cc`/`.h`, `software/system/product.cc`, `software/application/versions.h`, `software/application/update_u2p/update_common.h`, `update_u64.cc`, `update_u64ii.cc`, `update_binaries_u64.s`, `update_binaries_u64ii.s`. What they say, and what was built from it:

- An update file is a row of blocks (load address, length, start address, then the bytes); the loader copies each to its address and jumps to the last start address that is not zero. It checks nothing. The updater here walks the blocks the same way (`u64menu::inspect_image`) and refuses a file that is cut short, has no start address or starts outside what it loads, in its own words ("Image cut short: it would crash" …), since a real board would start such a file. The earlier condition "load address `$03000000`" is gone.
- A `.cfw` file's 36 bytes are the fingerprint, a product family (16 bytes) and a product name (16 bytes); what is given must match, else "Wrong Product Family" or "Update for Wrong Product"; a bad fingerprint is "Invalid Update Image". The 3.15a `.cfw` names the family "U64MK2" and no product. The families are "U64MK1" (Ultimate 64, Elite) and "U64MK2" (Elite II); so the u64 takes `.cfw` files for U64MK1 too.
- "Run Update" is offered for the product's own extension (`u64`, `ue2`) and for every `.cfw`; other boards' files have no such entry (before: an entry that failed).
- The updater switches the machine off five seconds after it is done on both boards (before: the u64 waited for a key).
- For the record, not rebuilt: the updater checks the FPGA image and the application it carries with a shift-and-add checksum against values fixed at build time, writes the drive ROMs, sounds and HTML files to the flash disk, flashes "Runtime FPGA" at 0 and "Ultimate Application" at `$290000` (U64), `$220000` (Elite II, XC7A50T) or `$3C0000` (XC7A100T), write-protects 4 MB, updates the WiFi module and asks "Reset Configuration? (Recommended)". Where the two images lie inside an update file is not fixed by the file's layout (the linker places them), so their checksums cannot be checked from outside without the build's symbols.

Tests: 17 for the machine, 82 in the crate, all pass (before: 16 and 81; new: `.cfw` family and product). The user's six 3.15a files walk through the loader's rules as expected (one block each, the start address inside it; the `.cfw` with family U64MK2; the `.u2r`, which has no header, fails the walk).
