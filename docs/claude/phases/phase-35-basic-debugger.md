## Decisions (user, 2026-11-13/14)

- **Scope "full":** listing (detokenised), current line and statement, breakpoints on lines, steps by line and statement, step over a GOSUB and step out, variables read and written, the GOSUB/FOR stack. Not chosen: watchpoints on variables, conditions on BASIC breakpoints, a line trace.
- **Machines:** all with a BASIC in ROM, in milestones by dialect family, Commodore first. BASICs loaded from disk or tape (AmigaBASIC, Microsoft BASIC on the Mac, the IMSAI's 8K BASIC and MBASIC) stay out.
- **Frontends:** the native protocol and `polydbg` only. No panel in the desktop or web frontend (the team's own IDE speaks the native protocol).
- **Core trait:** `Machine::basic()` as a new method with a default (`None`), as `gfx_views` was added. Approved.

Own choices (not asked): the types and the trait `BasicDebug` in `mimic-core::basic`; stop points as ordinary breakpoints the machine names and the session arms; the toy BASIC machine in `mimic-core::testing::basic` for tests without ROMs; BASIC breakpoints numbered apart from `break_add`'s; a line breakpoint stops when the program enters the line (not when a loop returns into it); the first step from a machine that sits before a statement's dispatch stops at that statement; a shared crate `basic-dialects` for the decoders from M1 on.

## Design

- **`mimic-core::basic`:** `BasicDebug` with `info` (dialect, granularity, memory space), `state` (mode inactive/direct/running, line and statement, text pointer, GOSUB depth), `program` (lines with number, address, raw bytes, text in Unicode and the offsets of the statements in it), `variables`, `array`, `stack`, `set_variable` and `stop_points`. All reads are peeks (golden rule 2).
- **Stop points:** the machine names the places where its interpreter begins a statement or a line as `BreakpointKind`s — an exec address in the dispatch loop, or a watchpoint on the "current line" variable — each with its granularity (`statement` or `line`). Contract: when one stops the machine, `state()` already reports the statement about to run.
- **Session (`mimic-debug/src/session/basic.rs`):** while a BASIC breakpoint is enabled or a BASIC step runs, the session keeps hidden breakpoints at the stop points (asked for again before every run, since ROM banking may move them); at each hit it reads `state()` and resumes silently unless a breakpoint or the step is satisfied. With nothing active nothing is armed (golden rule 5); no `tick` path of any machine changed. A breakpoint of the user's at a stop point's address still stops.
- **Steps:** `statement` — the next stop point; `line` — the next one in another line or at a line's first statement (into subroutines); `over` — the same with at most as many GOSUBs open as at the start; `out` — the next one with fewer GOSUBs open. All asynchronous, ended by `stopped` with the reason kind `basic_step` (`basic_break` for breakpoints), the line and the statement.
- **ROM versions (from M1):** system variables are stable over ROM revisions; dispatch addresses are found by a byte pattern in the ROM, not hard-wired, so patched ROMs (JiffyDOS) work. Without a match the machine offers line granularity only.
- **Protocol 11:** `basic_info`, `basic_state`, `basic_list {from, to}`, `basic_vars`, `basic_array {name, first, count}`, `basic_set_var {name, index, value}`, `basic_stack`, `basic_break_add {line, statement, enabled}`, `basic_break_remove`, `basic_break_enable`, `basic_break_list`, `basic_step {kind}`, `basic_run_to {line, statement}`; `"basic": true|false` in `capabilities`. `polydbg basic …`.

## Status

2026-11-14: **M0 done.** `mimic-core::basic` (types, `BasicDebug`, `Machine::basic()`), the toy machine `mimic-core::testing::basic::ToyBasic` (an interpreter in Rust that keeps its state in the machine's RAM, one statement every 8 cycles, one stop point; LET, add, GOTO, GOSUB/RETURN, FOR/NEXT, END; integer variables, an array, a string, a float; savestates; an option for line granularity; 7 tests), the session's BASIC debugger (9 tests, one more for a machine without a BASIC), protocol 11 with the contract test `debug_protocol::basic_debugger`, `polydbg basic` with its unit test and the end-to-end test `python_client::command_line_client_debugs_basic`. No real machine offers a BASIC yet: `capabilities` says `"basic": false` for all of them until M1.

2026-11-14, later: **M1 done.** New crate `basic-dialects` (trait `Dialect`, macro `impl_basic_debug!`; the decoders read the machine through the main CPU's `DebugTarget`, so a machine adds a field, three lines in `Machine::basic()` and the macro) with `cbm::CbmBasic` for Commodore BASIC (9 tests against a hand-built memory image). `machine-c64`, `machine-vic20` and `machine-pet` offer it. Nothing in it is tied to a ROM revision: the statement loop (`JSR …: JSR GONE3: JMP NEWSTT`) and the keyword table are searched in the CPU's view of $8000–$FFFF, the zero-page layout follows from the TXTPTR operand NEWSTT uses, the keywords in the listing are the ROM's own. The stop point is `JMP ($0308)` on the VIC-20 and C64 (before the IGONE vector, so wedges are followed) and the loop's first JSR on the PET. The gate test `tests/tests/basic_debug.rs` (`--ignored`, real ROMs) passes on the **C64, VIC-20, PET 2001 (BASIC 1.0), PET 3032 (BASIC 2) and PET 4032 (BASIC 4.0)**: it types a program in, lists it, stops at a line breakpoint after RUN, steps by statement through a FOR loop (frame with variable, limit and step), writes a float, an integer and a string variable the program then uses, steps by line into a GOSUB, out of it and over it, runs to a statement and finds the stack while halted inside statements.

Found on the way: after a cold start CURLIN is not $FFxx on BASIC 2 and later, so "running" also needs TXTPTR inside the line CURLIN names; BASIC 2 and later leave the statement loop's return address on the stack above each GOSUB frame (BASIC 1.0 does not); BASIC 4.0's loop calls a routine of its own instead of CHRGET (the first pattern expected `JSR $0070`).

Limits of the Commodore decoder: a string variable can only be overwritten in place with a string of the same length, and not a literal inside the program text (BASIC 4.0's heap has back pointers; changing lengths would need the interpreter's own allocation); statements behind THEN are part of the IF statement (the interpreter does not pass its loop for them); functions (DEF FN) are not listed; characters without a plain counterpart show as `{$xx}` (upper case/graphics set assumed); while INPUT reads its buffer the mode shows as direct; with the BASIC ROM banked out (C64 $01) the mode is inactive. Not checked: a cartridge or wedge that replaces the statement loop altogether, the 8032/8296 and SuperPET models (same BASIC 4.0 ROM as the 4032).

2026-11-14, later still: **M2 done for the C16, Plus/4 and C128; the MEGA65 waits.** `cbm::CbmBasic` now finds two families of interpreters. BASIC 3.5 and 7.0 keep `JMP ($0308)` but read the text through RAM routines, so their loop is found by the line step behind the jump (`STA CURLIN : INY : JSR … : STA CURLIN+1 : TYA : CLC : ADC TXTPTR : STA TXTPTR`), which also gives CURLIN and TXTPTR (TXTTAB is CURLIN − `$0E` in every version). Their GOSUB, FOR and DO frames are on a stack of the interpreter's own: the pointer is the operand of GOSUB's `LDA #$8D : STA (ptr),Y`, the top the constant CLR loads into it (Plus/4 `$7C`/`$07B0`, C128 `$7D`/`$09FF`); frames are read from the pointer to the top, so the stack is exact also inside a statement. FOR's text pointer is stored high byte first there. BASIC 7.0's tables for the `$FE nn` and `$CE nn` tokens follow the first keyword table. New in the core: `BasicFrame::Do` (protocol: a frame of kind `do`; no new version, the frame list only gained a kind).

Machines: the decoder reads data from a RAM space where ROMs hide RAM (`CbmBasic::with_ram`): the C16/Plus/4 got the space `ram` (`RAM_SPACE`, id 1) for it, the C128 uses its 128 KB `ram` space with the variables at `$10000`; `basic_info` names that space and all line and variable addresses are in it. While one of the interpreter's RAM routines has the ROM switched off (CHRGET on the Plus/4, the bank routines on the C128) the decoder stays valid as long as the CPU sees RAM where the ROM was. The C128 scans from `$4000` and hands the decoder its 8502 (`impl_basic_debug!` with a third argument), whatever processor the debugger addresses; in C64 mode the same decoder finds BASIC V2. Gate: `basic_debug` passes on the **Plus/4, C16, C128 and the C128 in C64 mode** (after `GO64`); a second part (`loops`) checks a DO loop around a FOR loop with both frames, and the listing of `SOUND`/`COLOR` (3.5) and `BANK`/`POT`/`SLOW` (7.0, two-byte tokens). 6 more unit tests against an image laid out like a C128 (15 in the crate).

Changed for all Commodore machines: the place reported is the line the text pointer is in, not the line CURLIN names — halted inside RETURN, NEXT or LOOP the two disagree for some instructions (on BASIC 3.5/7.0 long enough that the gate hit it), and the mode showed as direct.

**MEGA65 (my decision, 2026-11-14):** not built. The only ROM in the folder is the Open ROMs of 2021-08-24, whose BASIC is unfinished (`A=1` and `PRINT 3` answer ?NOT IMPLEMENTED ERROR, Phase 33 M4), keeps no Microsoft statement loop or keyword table (neither pattern is in `mega65.rom`) and could not run the gate program. BASIC 65 comes with the official ROM 920xxx, for which Phase 33's M7 waits too (deferred there by the user); the decoder for it follows when the ROM is in the folder. `capabilities` says `"basic": false` on the MEGA65 until then.

Not checked in M2: BASIC 3.5/7.0 programs with TRAP/RESUME, the C128 with a function ROM or a cartridge in C128 mode, the 3-plus-1 software banked in on the Plus/4 (the decoder then reports inactive, as with any other ROM there), GRAPHIC modes that move the program start (TXTTAB is read, so it should follow).

2026-11-14, M2b: **Simons' BASIC and TSB on the C64, as cartridges.** Both hook the vectors `$0300`–`$030B` and return to the ROM's statement loop after each of their commands, so the stop point (the ROM's `JMP ($0308)`), the variables and the GOSUB/FOR frames needed nothing. Added in `cbm::CbmBasic`, looked for only while IGONE points out of the ROM (and once per vector value, so another wedge costs one look): the keyword table (`HIRES`, `PLOT` …; words ending with `@` in Simons' BASIC, with bit 7 in TSB) for the tokens `$64 nn` — the scanner takes the second byte with the first, since `LOOP` is `$64 $3A` in both and TSB's `DO` `$64 $22`; the statement dispatch, through which the handlers of EXEC, REPEAT and LOOP are found and in them the count and base of the stack each keeps (the same addresses in both, `$C617`/`$C62C`/`$C641`; Simons' BASIC's entries begin a byte later). EXEC is reported as a GOSUB frame and counts for the depth, so step over and step out work on procedures; REPEAT and LOOP are loop frames. `BasicFrame::Do` of M2 became `BasicFrame::Loop { word, from }` (protocol: kind `loop` with `word`) before it was committed. `basic_info` says `Commodore BASIC V2 + Simons' BASIC` or `+ TSB`.

Where the extension is: the TSB cartridge (Magic Desk) copies itself to RAM `$8000`–`$CFFF` and runs there, also behind the BASIC ROM; the Simons' BASIC cartridge stays ROM and keeps its keyword table in the upper 8 KB, which it switches off whenever the BASIC ROM runs — at every stop point. So the C64 got a memory space `cartridge` (`CART_SPACE`, id 5: ROML/ROMH as the cartridge would answer now) and the decoder looks there and in memory (`CbmBasic::with_cartridge`), taking the one whose stacks it finds. The C64's decoder now also reads its data from the `ram` space, so a halt inside an extension's routine that has the BASIC ROM switched off no longer shows as inactive (M1's limit "with the BASIC ROM banked out the mode is inactive" holds only while something else than RAM is mapped there).

New for it in the emulator: the Simons' BASIC cartridge type (CRT type 4, `devices-cartridge` `Scheme::SimonsBasic`: 8 KB, a write to `$DE00` switches ROMH on, a read off; read from the cartridge's own code). Gate: `basic_debug` `c64_simons_basic_cartridge` and `c64_tsb_cartridge` with the user's images (`Simons_Basic.crt`, `TSBneo_md_260228.crt`): the listing of a program with REPEAT/UNTIL, LOOP/EXIT IF/END LOOP, EXEC/PROC/END PROC with its statement offsets, the loop frames, a step into a procedure, its frame and depth, step out. Unit tests: 5 for the extension (both table formats, the vector unhooked, another wedge, the tokens, the stacks, the cartridge space; 20 in the crate), 1 for the cartridge type. The demo program on the user's Simons' BASIC disk (`DEMO S.BASIC`, 400 lines) detokenises with the table without an unknown token (checked by script).

Decided on the way: the disk versions of both extensions (the same interpreters loaded into RAM) passed the same test, but the user wants extensions supported as cartridges only, so those tests were removed again; nothing in the decoder refuses a RAM copy. **Not built (my decision):** the description of an unknown extension as a machine option — the two extensions named work without one, and a format for it should follow a real third case. Limits: the order between the ROM's GOSUB/FOR frames and the extension's is not known (separate stacks); Simons' BASIC's LOCAL/GLOBAL variables, ON KEY and ON ERROR handlers are not shown; CALL leaves no frame (it is a jump); only the C64 was tried (no VIC-20 or C128 extensions).

2026-11-14, conditional BASIC breakpoints (the user: "bau noch conditional breakpoints ein"; **protocol 12**): `basic_break_add` takes `condition` and `ignore`, `basic_break_condition {bp, condition}` replaces a condition, `basic_break_list` shows both, `basic_info` says `name_len`. The condition is an expression over the program's variables written as BASIC writes it (`mimic-debug/src/basic_expr.rs`: numbers, strings, variables with their type sign, array elements with one index, comparisons, `+ - * /`, `AND OR NOT`); the session reads the variables through `BasicDebug::variables()`/`array()` only when the program is at a breakpoint's place, so nothing changes for the hot path. For the names `BasicInfo` got `name_len` (the characters a dialect tells apart: 2 in Commodore BASIC, so `COUNT` finds `CO`). Every breakpoint at the place whose condition holds counts its hit; the first past its ignore count stops. My decisions: a language of its own beside `expr.rs` (registers and memory there, BASIC values with floats and strings here); `AND`/`OR`/`NOT` work on truth values, not bit patterns; arrays with one index only (the storage order of more dimensions is the dialect's); no BASIC functions (`LEN`, `PEEK` …); `basic_run_to` takes no condition. Tests: 5 for the language, 2 for the session, the contract test and the gate (`I = 3 AND C$ = "ABC" AND NOT QQ` on every machine of the gate); `polydbg basic break LINE [CONDITION]`, `basic cond BP [CONDITION]`.

2026-11-15: **M3, Applesoft done; Integer BASIC waits for a good ROM dump** (the user: "mach mit dem apple weiter"). Applesoft is the same Microsoft 6502 BASIC, so `cbm::CbmBasic` decodes it too (`machine-apple2` keeps one with `scan_from($D000)`); it is told by its keyword `HIMEM:`. Read from the user's Apple II+ ROM with the gate test's new tool `disassemble` (`BASIC_DIS=apple2:iiplus:d7d2:d830`, an `x` before the address dumps bytes): the statement loop `JSR CHRGET : JSR EXECUTE : JMP NEWSTT` has a branch between the jump and EXECUTE (the pattern now takes the second target 9 or 11 bytes behind the loop's start); TXTTAB is `$51` below TXTPTR (`$67`, `$B8`), not `$4F`; GOSUB is `$B0` and REM `$B2` (both tokens are now taken from the keyword table for every version); CLEAR resets the stack pointer to `$F8`, so the frames end below `$01F9`; variables, arrays, floats and the GOSUB and FOR frames are BASIC V2's, the loop's return address above a GOSUB frame included. The listing is LIST's (`$D6DA`): every byte from `$80` is a keyword, also inside quotes, shown with a blank before and behind it (the tokeniser drops the blanks typed), so `10 A=5:GOSUB100` lists as `A = 5: GOSUB 100`; text is ASCII. The gate test passes on the **II+, the IIe and the enhanced IIe** (started without the Disk II card, `slot6=none`, so they come up in BASIC); 4 unit tests for the flavour; the Commodore gates still pass (9 of 9).

**Integer BASIC (the original Apple II) is not built:** the user's dump of chip 341-0002 (`3410002_E800.Bin`, `$E800`–`$EFFF`) is defective — bit 4 is 0 in every one of its 2048 bytes (the other chips have it set in 34 to 42 % of theirs), so `STA $0100,Y` reads `89 00 01` and branches `80`/`C0`/`A0`/`E0`. Model `ii` reaches the `>` prompt and takes program lines, but RUN ends in the monitor with BRK (tried: `10 A=5:GOSUB 100` …). Found so far for the decoder, from the intact chips: the program lies between PP (`$CA`) and HIMEM (`$4C`), a line is length, number (2), tokens, `$01`; LIST (`$E06D`) reads the keywords backwards out of the syntax table at `$EC00`–`$EDFF` (the damaged chip); RUNFLAG is `$D9` bit 7; the text pointer PX is `$E0`; the FOR stack is ten tables of 16 from `$0140` indexed by `$FB`, GOSUB's count is `$FC`. Claude's decision: no decoder written blind against a ROM that cannot run; it waits for a good dump of 341-0002 (better all four chips).

Limits of Applesoft beyond the Commodore decoder's: `ONERR GOTO` handlers and `POP` are not shown as such (POP just removes the frame); `&` and USR extensions that never return to the statement loop are not followed; Applesoft loaded into a language card (on a II) was not tried; lower case in strings is shown as stored (the II+ has no lower case on its screen).

2026-11-15/16: **M4 done** (the user: "mache mit m4 weiter"): the TRS-80 with Level II BASIC (Model I, Model III) and with Level I BASIC, and MSX BASIC 1.0 and 2.0. Two new decoders in `basic-dialects`:

- `msz80::Z80Basic` (TRS-80 Level II, MSX). Microsoft's Z80 BASICs keep the text pointer in HL, but the statement loop stores it and the stack pointer at its top (`LD (SAVTXT),HL`, `LD (SAVSTK),SP`). The loop is found by these two stores before `RST 10H : LD DE,NEWSTT : PUSH DE`; that `RST` is the stop point. Place and stack are read from SAVTXT and SAVSTK, never from the registers: the statement is the one behind SAVTXT (the next line's first if it stands on a line's end), the frames start at SAVSTK. So both also hold while the machine is halted inside a statement, and they always belong to the same moment. The system variables are fixed addresses per machine family (TRS-80 `$40A2`…, MSX `$F41C`…), the keyword tables are read from the ROM.
  - **TRS-80** (read from the user's Level II ROM: loop `$1D1E`, GOSUB `$1EB1`, FOR `$1CA1`, LIST `$2B7E`, table `$1650`): a GOSUB frame is 5 bytes, a FOR frame 17 (single precision step and limit, or for an integer loop four unused bytes, step, limit); variables are type byte, the name's second then first character, the value (integer, string, single and double precision in Microsoft's binary format). The listing is LIST's: the colons the tokeniser puts before ELSE and before the tick's REM are hidden, but they begin a statement for the interpreter, so ELSE and `'` are statements of their own.
  - **MSX** (read from the user's MSX1 BIOS, the MSX2's is the same there: loop `$4601`, GOSUB `$47B2`, FOR `$4524`, LIST `$5284` and `$537E`, table `$3A72`): a GOSUB frame has a word for the event traps (7 bytes), a FOR frame 16 bytes for step and limit whatever the type (25 bytes; a single precision limit lies in two swapped halves); the name's first character comes first; floats are decimal (sign and exponent, then 6 or 14 BCD digits). The tokeniser packs constants (`$0B`–`$1F`: octal, hex, line numbers and line pointers, integers, single and double precision); the listing writes them out as LIST does, with `!` and `#` where LIST puts them and MSX BASIC's number format (plain up to 14 digits before the point and from 0.01, an exponent otherwise: `.001` lists as `1E-03`, `1E10` as `10000000000!`). The keyword table is alphabetical with a token behind each word; the first word of a token counts (GOTO, not GO TO); function tokens are `$FF nn`. Lines end where their links say (constants hold zero bytes). The default type is double precision, so that one has no sign and single precision shows `!`.
- `level1::Level1` (TRS-80 Level I, a Palo Alto Tiny BASIC with floats; read from the user's ROM: RUN `$038C`, GOSUB/RETURN `$04C4`, FOR/NEXT `$0546`, the statement's end `$0030`/`$08B3`, variables `$0038`/`$0BE8`). No tokens: the listing is the stored text. Two stop points, where a statement begins: behind the store of the line pointer (`$03A0`) and behind a colon (`$08B6`). The line comes from the pointer `$409F`, the statement from DE (exact at the stop points). GOSUB frames form a chain (`$40A3`); the one running FOR loop is in memory (`$40A5`…, step and limit are 16-bit integers), the others are saved on the stack by FOR and GOSUB and found as the first chain from SP that ends at `$4200`. Variables A–Z (4 bytes from `$4000`), A$ and B$ (16 bytes each). The number format was calibrated in the machine: mantissa without its leading 1, a signed exponent split over two bytes, −128 for zero; four zero bytes are 0.5.

`machine-trs80` keeps one of the two by its `level` option (enum `Basic`), `machine-msx` a `Z80Basic`. Gate tests (`tests/tests/basic_debug.rs`, all with the user's ROMs): `trs80` (Model I 1.3 and Model III: the standard gate plus `z80_extras`: an integer loop, double precision, an array, ELSE and the tick, a two-character name), `msx` (MSX1 and MSX2 with the real BIOS: the same two plus `msx_extras`: the listing of packed constants compared with what LIST writes into the video RAM, a single precision loop, the line pointer behind GOTO after a run), `trs80_level1` (its own program: breakpoint, steps, FOR, GOSUB, variables written, numbers as the ROM stores them, loops saved by FOR and GOSUB). 12 of 12 gate tests pass; 16 unit tests for the two decoders against hand-built images. The tool `disassemble` takes machine options (`BASIC_DIS=trs80:1:0380:03c5:level=1`).

Limits: MSX event traps (ON KEY/STRIG/INTERVAL GOSUB) push their frame between the stores of SAVSTK and SAVTXT, so at the handler's first statement the depth is still the old one; with a cartridge or the disk ROM paged over the BASIC ROM the mode is inactive for that moment; `DEFINT` and its kin are not looked at for the names (a variable made integer by `DEFINT A` shows as `A%`); double precision values pass through an f64 (14 BCD digits fit, 16 binary digits of the TRS-80's 17 do); Level I's array `A()` is not listed (it has no size), and a statement behind THEN is part of its IF; halted inside a Level I statement the statement number relies on DE being the text pointer. Not checked: the Model I ROM 1.2 and the System 80 ROMs (same code by the patterns), Level II with the Expansion Interface's Disk BASIC (a BASIC loaded from disk: out of the phase), MSX2 screens other than 0 for the LIST comparison.

2026-11-16: **M5 done** (the user: "weiter mit M5 Sinclair"): Sinclair BASIC on the ZX81 and on the Spectrum 48K, 128K and +2, one decoder `sinclair::Sinclair` with two layouts.

- **Place.** PPC is the line, on the Spectrum SUBPPC the statement (from 1); a command typed in runs as line −2 on both. The Spectrum's stop point is in the statement loop behind the count of SUBPPC and the look at the statement's first character (`LD HL,STMT-RET`, 48K `$1B3D`), found by the loop's bytes. The 128K and the +2 have a second copy of the loop in their editor ROM (`$17D6`, +2 `$17F5`; a `JP Z` where the 48K has a `JR Z`), which runs programs in 128 BASIC; in 48 BASIC the other ROM's runs. The ZX81 has one statement per line; its stop point is behind `LD (PPC),DE` in the line loop (`$0699`).
- **Stop points in the ROM space.** With two ROMs at the same addresses a breakpoint in the CPU's view would also hit the other ROM's code. `machine-spectrum` therefore checks execution breakpoints in its memory space `rom` too (address = ROM number × 16 KB + address), only while that ROM is paged in and no Multiface, Interface 1 or Beta Disk ROM lies over it; the stop points are such breakpoints. The check sits in the branch that runs only with a debugger attached, next to the one for the CPU space, so nothing changes without breakpoints (golden rule 5; not benchmarked for that reason).
- **Statements.** A colon and THEN both begin a statement on the Spectrum (the ROM's EACH-STMT counts both, and IF jumps back into the loop), so `IF a THEN LET x=1` is two statements — unlike in every dialect before. The loop is also used to check the syntax of a line typed in, with FLAGS bit 7 clear: the place is reported only with it set.
- **Running or not.** On the Spectrum ERR_SP points to the return address into the main loop while a line runs (`$1303`, in 128 BASIC `$5B1D`; both read from the ROMs); the editor puts its own handler there with the old ERR_SP above it, which is followed for the stack, and FLAGX bit 5 tells INPUT's editor from the editor proper. The ZX81 has nothing on its stack between two lines; there the line loop's `$C0` in the high byte of X_PTR, which the editor clears, marks a running program (found by comparing the system variables at a stop point and after BREAK).
- **Stack.** GOSUB frames lie above the word ERR_SP points to, up to the end marker `$3E`: line and next statement (3 bytes) on the Spectrum, line + 1 on the ZX81. There is no FOR stack: FOR turns its variable into a control variable with limit, step and the place to loop to, and it stays one after the loop. A loop is reported while its value has not passed its limit, behind the GOSUB frames, the latest in the program first.
- **Variables.** Six kinds by the top bits of the first byte: numbers with short and long names, FOR variables, strings, arrays of numbers and of characters; five-byte floats, on the Spectrum also its small integers (written for whole numbers up to 65535). Arrays report their dimensions as DIM gives them; an array of characters has single characters as elements.
- **Listing.** As LIST writes it: the ROM's keyword table, the blanks before and behind keywords by the ROM's rules (Spectrum PO-TOKENS; ZX81 `$094B` with its flag that holds back a leading blank), the five hidden bytes behind every number skipped. On the Spectrum text is ASCII with £, ©, ↑ and the block graphics; colour codes and user-defined graphics show as `{$xx}`; `$A3`/`$A4` are SPECTRUM and PLAY on the 128K. The ZX81's own character set is mapped to Unicode, inverse characters show as `{$xx}`.

`machine-zx81` and `machine-spectrum` keep the decoder; it looks at the ROMs once. Gate tests in `tests/tests/basic_debug.rs`: `zx81` (its own program of eleven lines: the listing compared with what the ROM lists into the display file, breakpoint, steps, the loop, GOSUB into, out and over, variables written, the frame inside a statement, a condition, BREAK back to the editor) and `spectrum` (the gate's program with LET and a line 5 on the 48K typed by keyword keys, on the 128K and +2 typed as text in 128 BASIC and by keys in 48 BASIC; `spectrum_extras`: the statement behind THEN, both kinds of arrays read and written, a long name, a loop counting down around a GOSUB, floats and small integers written, and after STOP the editor is not a running program). 14 of 14 gate tests pass (12 before); 9 unit tests for the decoder against hand-built images (49 in the crate).

Own choices (not asked): names are reported in upper case (the interpreter ignores case and stores lower case) and looked up without regard to case or blanks; the order of loops among themselves and against the GOSUB frames is a rule of thumb, since the interpreter records none; the dialect names `Sinclair ZX81 BASIC`, `ZX Spectrum BASIC` and `ZX Spectrum 128 BASIC` (by the ROM set, also while a 128K runs 48 BASIC); execution breakpoints in the Spectrum's `rom` space instead of a change to the session.

Limits: a loop left by GO TO stays listed as open until its variable is used again; a BASIC step taken while a line is typed in stops at that line's syntax check (the same loop, reported in direct mode without a line); between the store of PPC and of SUBPPC (a few instructions when a line begins) the statement number is the old one; while INPUT waits on the ZX81 the mode shows as direct; strings and array elements are written in place only (the same length); DEF FN functions are not listed; with an Interface 1, Multiface or Beta Disk ROM paged over the BASIC ROM no stop point hits (their code does not run statements). Not checked: the TS1000 (the same ROM), the ZX81 editions 1 and 2 (the same bytes at the patterns), the 128K's calculator and tape loader, programs with machine code that moves the stack, Interface 1 commands (they run through the error handler in the shadow ROM and return to the loop).

2026-11-16: **M6 done** (the user: "weiter mit M6"): Atari BASIC on the Atari 400/800/XL/XE (`atari::AtariBasic`) and Locomotive BASIC 1.0 and 1.1 on the CPC 464, 664 and 6128 (`locomotive::Locomotive`).

**Atari BASIC.**

- **Program.** Every line is tokenised when entered, down to variables (a number each), numbers (six bytes) and operators; a line is a chain of statements, each with the offset of the next. The line typed in last is stored behind the program as line 32768 and run from there. What follows THEN is a statement of its own (as on the Spectrum).
- **Place.** STMCUR is the line, NXTSTD the offset of the statement after the current one; the statement is the one whose successor NXTSTD names. The stop point is the statement loop's call of the statement (`$A977`), found by the loop's bytes.
- **Running or not.** The editor and every entry into the loop set the stack pointer to `$FF`, so the first address on the 6502's stack (`$1FE`) lies in the loop while a program runs: the return address of the statement's call, of the loop's test for BREAK or of its step to the next line, or the place where an interrupt met the loop. Found the hard way: at the stop point itself the test for BREAK's return address is there, not the statement call's. A line number below 32768 is the second condition.
- **Stack.** Between RUNSTK and its top: GOSUB four bytes (0, the line, the offset of the statement's token), FOR the limit and the step and the same four bytes with the variable's token.
- **Variables.** A table of names and a table of values of eight bytes; numbers are decimal (ten digits, exponent of 100). A string has a dimensioned length: the debugger writes any length up to it (the only dialect so far where a string can grow). Arrays have one or two dimensions; one dimension is stored like `DIM A(n,0)` and both are reported with one.
- **Listing.** As LIST writes it: both name tables from the ROM, a blank behind every statement name, blanks around operators that are words, numbers in the floating point package's format (`1E+10` but `1.0E+11`: the first pair of digits keeps its zero; found by comparing with the screen).
- The XL/XE can switch the ROM off: the decoder checks the loop's bytes every time and reports `inactive` without them.

**Locomotive BASIC.**

- **Program and variables lie under the lower ROM**, so they are read from the memory space `ram` (which `basic_info` names), not from the Z80's view.
- **Place.** The statement loop stores the address of the byte before the statement it begins and, per line, the address of the line's number, which is 0 while a command typed in runs and at the prompt: that is the mode. The statement is found by walking the line's tokens (a `&01` inside a number is no separator). What follows THEN, and ELSE's branch when the condition fails, run without passing the loop; ELSE and the tick begin statements behind a colon LIST hides.
- **Stop point in the ROM space.** BASIC shares `&C000` with the disc ROM. `machine-cpc` has a new memory space `rom` (OS, BASIC, disc ROM) and checks execution breakpoints there while that ROM is the one switched in, as the Spectrum does since M5; the check sits in the branch that runs only with a debugger attached (golden rule 5; not benchmarked for that reason).
- **Stack.** BASIC's own, every entry ending with its length: GOSUB 6, WHILE 7 (reported as a frame of kind `loop`), FOR 16 with an integer and 22 with a real variable; the FOR entry names its variable by the address of its value.
- **Variables.** Two areas walked entry by entry (integer, string, real; arrays with the last dimension's size first and the first index running fastest). DEF FN's functions are entries with bit 6 set in the type and are skipped. A string assigned from a constant points into the program's text: the debugger refuses to write there.
- **Listing.** LIST's rule read from the ROM: the text as stored, a blank only where a word, a name or a number would run into the next one; the keyword table (26 lists by first letter and one of symbols) from the ROM; real numbers with nine digits. Compared with the screen in the gate test, whose bitmap is matched against the characters in the OS ROM.
- The system variables' addresses differ between 1.0 and 1.1 and are taken from the operands of the ROM's own code; the stack's and the variables' layouts are the same in both.

Gate tests: `atari8` (800XL, 130XE and the 800 with the cartridge: a gate program of its own with DIM for the string, and `atari_extras`) and `cpc` (464, 664, 6128: the common gate `gate_with`, which now takes the program as typed, and `cpc_extras`). 16 of 16 gate tests pass (14 before; new and green: `atari8`, `cpc`). 12 unit tests for the two decoders against hand-built images (61 in the crate).

The CPC's typist typed capital letters without SHIFT, so strings arrived in lower case; capitals now hold SHIFT.

Own choices (not asked): the dialect names `Atari BASIC` (without the revision), `Locomotive BASIC 1.0` and `1.1`; the memory space `rom` on the CPC instead of a change to the session; capitals with SHIFT in the CPC's typed text (a change for `type` and paste: text arrives in the case it was written in) and the longer gap on the Atari (typing is a quarter slower there); names on the CPC in upper case with `%` and `$`, a real variable without `!`; `DIM A(n,0)` reported with one dimension; the refusal to write a string constant in the program; the gate tool's `BASIC_DIS_RUN` and `BASIC_DIS_LOAD`.

Limits: on the Atari a jump under way shows the new line with its first statement a few instructions early; `DIM A(n,0)` and `DIM A(n)` cannot be told apart; a string is written with ASCII characters only. On the CPC a GOSUB from a command typed in has line 0 as its origin; a program that switches the 6128's RAM banks under BASIC is read from the base 64 KB. Not checked: Atari BASIC revisions A and B (the patterns are the loop's bytes, the tables are found through LIST's code), Turbo-BASIC and other BASICs from disk (not in scope), the CPC's AFTER/EVERY and ON BREAK subroutines (stack kinds 1 and 2), CHAIN MERGE, other languages' ROMs, the CPC Plus.

2026-11-20: **M7, BBC BASIC II and IV done** (the user: "mache bei phase 35 weiter. komplettiere die basic debugger"). One decoder, `bbc::BbcBasic`, kept by `machine-bbc` for the Model B, B+ (BASIC II) and the Master (BASIC IV).

- **Place.** There is no "current line" variable: the text pointer is a base (`&0B`) and an offset (`&0A`), and every statement's end moves the base to the delimiter and sets the offset to 1. The stop point is in the statement loop's entry behind the skip of blanks (`CMP #&CF`, BASIC II `&8BAD`, BASIC IV `&9015`), found by the loop's bytes; there the base plus the offset less 1 is the statement's first character. The line is the one the pointer lies in (a line owns the bytes behind its `&0D` up to the next line's `&0D`, a statement its delimiter). A base in page 7 is the direct mode, as for the ROM itself. Found the hard way: the statement's end stores the new base three instructions before the new offset; halted in between (the gate did, on the Master) the pointer is wrong, so that window is recognised by the program counter.
- **Statements.** A colon begins one; so do THEN and ELSE unless a line number follows, and what stands behind REPEAT, because the interpreter enters its loop for each. An empty statement (`REPEAT:`, `::`) passes the loop as well and is counted, so every hit of the stop point is a statement of its own. REM, DATA and a `*` command take the rest of the line. A procedure's entry passes the loop at the end of its `DEF` statement and is reported there.
- **Stacks.** GOSUB and REPEAT keep pointers in tables with a count, FOR entries of 15 bytes (variable address and type, step, limit, the base behind the FOR statement). BASIC IV has the REPEAT tables and the FOR entries elsewhere (`&0500`/`&0514` and `&0528` instead of `&05A4`/`&05B8` and `&0500`), so all table addresses are read from the operands of the ROM's own code. PROC and FN copy the 6502's stack to BASIC's own stack, set the stack pointer to `&FF` and push their token, the caller's text pointer and the count of variables saved for parameters and LOCAL; the callers are found by walking BASIC's stack (the saved variables, then the saved 6502 stack; if values of an expression under way lie in between, the next thing that has the shape of a saved stack). A call is a frame of kind `gosub` and counts for the depth, so step over and step out work on procedures and functions.
- **Variables.** The resident integers `@%`, `A%`–`Z%` (listed while not 0, writable always) and the chains by first character: integers, reals (five bytes), strings (address, room, length: written in place up to the room), arrays with their sizes (the last index runs fastest). Names keep their case.
- **Listing.** LIST's with `LISTO 0`: the text as stored, tokens written with the ROM's own keyword table, line numbers behind GOTO and its kin unpacked, nothing expanded inside quotes. The blank typed behind a line number is stored with the line and so part of the text (the gate types its program without it).

Gate: `basic_debug` `bbc` (Model B, B+, Master): the common gate, and `bbc_extras` (REPEAT with its empty statement and frame, the statements behind THEN and ELSE, arrays read and written, a function called inside an expression and a procedure as frames with step out and over, an integer loop on a resident variable, a string grown to its room, reals written, END back to the prompt). 17 of 17 gate tests pass (16 before; new and green: `bbc`). 6 unit tests against a hand-built image, for both ROM layouts (67 in the crate).

Own choices (not asked): the dialect names `BBC BASIC II` and `BBC BASIC IV` (by the ROM's copyright year); resident integers listed only while they are not 0; calls reported as GOSUB frames; the order loops, GOSUBs, calls in the stack list (each kind has a stack of its own, their order among each other is not recorded); the stop point kept while another sideways ROM is switched in (the filing system during a statement), where it reports as inactive.

Limits: `IF a PRINT …` without THEN runs its statement through the loop but is not told from the IF statement (no marker in the text); a statement number inside the assembler's `[ … ]` means nothing; ON ERROR handlers and the values LOCAL saved are not shown; a string is written in place only (up to its room); between the two stores of a base (GOTO, RETURN: one instruction) the place may be wrong; while another sideways ROM runs (a filing system call, VIEW) the mode is inactive. Not checked: BASIC I (the same loop bytes are expected, `&81`-year ROMs are named BASIC I), BASIC 4r32 of the Master Compact, HIBASIC on a second processor (no Tube), programs that move PAGE while running.

2026-11-20, the same day: **HC-BASIC on the KC85/3, /4 and /5** (it was to join in the KC85's own phase; done here with "komplettiere die basic debugger"). The stop point is the loop's call for the statement's first character (`$C88A`), found as the call before `LD DE,loop : PUSH DE`. 2026-11-20, later: **M8, TI BASIC on the TI-99/4A done.** The risk named below did not come true: TI BASIC is written in GPL, but its statement loop and the common statements are machine code in the console ROM, so the stop point is an ordinary execution breakpoint and `DebugHooks` needed nothing new. Decoder `tibasic::TiBasic`; `machine-ti99` hands it its three memory spaces (the CPU's view for the scratch pad and the console ROM, the video RAM, the GROMs).

- **Place.** EXTRAM (`>832E`) points into the line table, at the text address of the line being run; PRGFLG (`>8344`) is 0 while a typed command runs. Every line of a program begins at one place in the console ROM (`>1976`, `LIMI 3 : LIMI 0 : CLR @>83D6`, found by these bytes): the loop comes there for the next line, GOTO and GOSUB branch there, and RETURN and NEXT set EXTRAM back and let the loop step on. That is the stop point. There is one statement to a line, so the granularity is `statement` and every line has the one statement 0.

2026-11-21: **M7 complete: BBC BASIC V on the Archimedes** (BASIC 1.05, the module in RISC OS 3.11). Decoder `bbcarm::BbcBasicV`, kept by `machine-archimedes`.

- **Place.** The text pointer is the register R12 while statements run. Every statement begins with a jump through a table by its first byte (`LDRB R10,[R12],#1 : LDR R4,[PC,R10,LSL #2] : ADD PC,PC,R4`, `&38B204C`; found by these three words in the ROM); the stop point is the second instruction, where R10 is the byte and R12 points behind it. The line is the one the pointer lies in, as for the 6502 version.
- **Blanks pass the loop.** The table sends a blank, a colon and the line's end back to the same jump, so the stop point is reached for each of them before the statement proper (lines typed with a blank behind the number have one in every line). At such a hit the decoder reports `running` without a place. **New in the contract** (`mimic-core::basic::BasicState`, `mimic-debug` `basic_hit`): running without a place at a stop point means "between two statements"; the session runs on without counting it for a step or a breakpoint. No other decoder reports that combination, so nothing changed for them (the 19 other gate tests pass unchanged).
- **Workspace.** R8 points to it (`&8700`): PAGE, TOP, the variables' end, LOMEM and HIMEM are words below it, the resident integers 256 bytes below, the heads of the variable chains 512 bytes below. BASIC is "active" while these lie in order and the program begins with a line; in the Supervisor or the Desktop the registers hold other things and the mode is inactive.
- **Stack.** One stack (R13) for everything; a frame begins with a word that names it (`&F8` GOSUB, `&FD` REPEAT, `&CE` WHILE, `&ED`/`&E3` FOR with an integer or a real variable, `&F2` PROC, `&A4` FN). Saved variables and values of an expression under way lie between the frames unmarked, so frames are found by their shape: the mark and, where the frame has them, pointers into the program and to a variable. PROC and FN are frames of kind `gosub` and count for the depth; WHILE and REPEAT are frames of kind `loop`.
- **Variables.** As on the 6502 with 32-bit links; integers and an array's address are in the next aligned word behind the name, the five bytes of a real or a string descriptor are not (found when `LONG%` read wrong). A real's mantissa is stored low byte first. A string is written in place with the same length.
- **Listing.** LIST's with `LISTO 0`: the ROM's keyword table (word, token, a flag byte that tells the tokens of two bytes and their prefix `&C6`/`&C7`/`&C8`), line numbers unpacked.

## Risks and open items

- **BBC BASIC** has no "current line" variable: the line is found from the text pointer, the stop point only by a ROM pattern. (Done 2026-11-20/21: so it is.)
- **TI BASIC** is not machine code: a stop point there needs a breakpoint on a GROM address, which `DebugHooks` may not offer yet; at worst line granularity. (Done 2026-11-20: its statement loop is machine code in the console ROM; nothing new was needed.)
- **Archimedes:** BBC BASIC V is a RISC OS module with its workspace behind a register; the least certain part, hence last in M7. (Done 2026-11-21; it needed a small addition to the contract, see Status.)
- **Atari BASIC** tokenises at entry and keeps a table of variable names: a decoder of its own.
- **MEGA65:** waits for the official ROM (see Status, M2). ROM builds move addresses often; only the pattern search carries there.
- **Watchpoint stop points** fire at the first byte written; a machine that uses one on a two-byte line variable has to watch the byte written last (contract above). Not exercised by the toy machine, which uses an exec stop point.
- **Sources:** token tables and system variables come from documentation only (Mapping the C64, the Atari BASIC Source Book, the Spectrum ROM disassembly …), never from another emulator's source; each goes into `docs/sources.md` with its milestone.
- Not in the phase: panels in the desktop and web frontends, loaded BASICs, watchpoints on variables, conditions on BASIC breakpoints, a line trace, entering or changing program lines through the debugger. Machines still to come (Colour Genie, QL, KC85) join `basic-dialects` in their own phases.
