# Debug server and live preview

Part of the project's instructions for Claude Code; the core is `CLAUDE.md` at the repository root, the index of these files is its section "Further documentation".

- Listens on `127.0.0.1` only by default; remote binding requires `--debug-bind` **and** a token.
- Emulation runs on its own thread; the server communicates via a command queue + event channel. Never lock the emulation thread from a network task.
- **Native protocol** (binary over TCP, JSON over WebSocket, same message set; Phase 1 ships JSON lines over TCP, documented in `mimic-debug/src/protocol.rs`, contract test in `tests/tests/debug_protocol.rs`):
  - Session: `list_machines`, `attach`, `capabilities`
  - Execution: `pause`, `resume`, `step_instr`, `step_over`, `step_out`, `step_cycle`, `step_line`, `run_to`, `step_frame`, `reset`
  - Raster: `beam` position, `step_line` (follow a frame being drawn line by line, with the partial frame), raster trace (instructions and traced reads/writes stamped with frame/line/cycle; ring buffer in `DebugHooks`, zero cost when off)
  - Breakpoints: exec, read/write watchpoints, chip-register I/O, raster line/cycle, IRQ/NMI; conditions + hit counts
  - Inspect/modify: registers, memory (peek, bank-aware), disassembly, chip registers, stack
  - State: `save_state`, `load_state`, rewind ring buffer
  - Symbols: VICE labels, cc65 `.dbg`, KickAss `.sym`, sjasmplus `.sld`, m68k ELF/hunk symbols
  - Push events: `stopped`, `breakpoint_hit`, `frame_ready`, trace stream, `media_changed`, `device_connected`
  - Devices: see `docs/claude/freezer.md`
- **Adapters** translate to: VICE binary monitor (port 6502, all Commodore 8-bit machines). A GDB remote stub was built and dropped on 2026-10-22 (user decision): stock GDB has no 6502 and crashes stepping a Z80, so it would not work for every machine. DAP is deferred too (user decision 2026-10-22: the team has its own IDE on the native protocol).
- **Graphics data views** (Phase 8; trait extension approved and built 2026-10-25, see `docs/claude/phases/phase-08-expansion.md`): where a machine has them, the debugger also delivers the graphics the video chip works from, decoded and raw, without the debugger knowing the chip:
  - `Machine::gfx_views() -> Vec<GfxViewInfo>` (default: none) and `Machine::gfx_view(id, opts) -> Option<GfxView>`; a view is a kind (`sprites`, `charset`, `bitmap`, `screen`, `tiles`), a name ("VIC-II sprites", "ANTIC charset $E000", "GTIA players", "Amiga bitplanes"), the source memory space and address range, its parameters (size, colours, multicolour/hires, current bank/pointer) and a picture as indexed pixels + palette (same type as `FrameRef`), plus the raw bytes.
  - Examples: C64 VIC-II — 8 sprites (pointers, positions, colours, multicolour, expansion) and the current charset/bitmap/screen RAM by bank; C128 VDC charset; TED/VIC charsets; Atari — players/missiles, the character set at CHBASE, the display list's playfield memory; Amiga — sprites, bitplanes, Copper-set palettes; CPC — screen memory in the current mode; BBC Micro — the 6845/Video ULA screen (teletext through the SAA5050), the palette and the SAA5050 character set; MEGA65 — the VIC-IV display area, the character set, the sprites and a palette bank.
  - Options select what a view shows (e.g. a different charset address, colours, sprite number), so a debugger can browse memory as graphics.
  - Native protocol: `gfx_list`, `gfx_get {view, format=png|qoi|indexed, scale, options}`; the preview server serves the same as `/gfx/<view>.png`; `polydbg gfx`. Contract tests for each.
- **Vector displays** (protocol 10, 2026-11-11): `vectors` returns the last complete frame of a vector display (`Machine::vectors`, the Vectrex): size in coordinate units, `cycle_hz`, `frame_cycles`, `frame`, `phosphor`, `style` and every segment as `[x0, y0, x1, y1, intensity, r, g, b, cycles, at]` in drawing order (`at`: the cycle in the frame it began); machines without one answer with an error, `capabilities` has `"vectors": true|false`. The preview serves the same as `GET /vectors.json`, and its stream with `filter=crt` draws vector frames through the phosphor stage (the frame copies carry the segments, `OwnedFrame::vectors`). `polydbg vectors [--all] [--svg FILE]`. JSON form in `mimic_preview::vectors_json`; contract test `vector_display_segments`.
- **Typed text / paste** (protocol 13, 2026-11-15): `Machine::typed_keys(text, start) -> Option<(events, end)>` (default none) gives the key events that type a text on the machine's keyboard; the machines build them from their own key tables (`keyboard::typed_events`, `typing.rs`) with a pause behind RETURN (`mimic-core::input::typed_lines`). `mimic-core::input::TextFeed` holds text on the host side and hands it over line by line (so the input queue stays short and the rest can be dropped); the session, the web app and headless each own one and pump it before a frame, and the events go through `Session::input` like the user's keys (recordings carry them).
- **Speed steps and warp** (2026-11-17): the desktop's footer slider has the steps -4x, -3x, -2x (that many times slower), 1x to 10x and warp (`--speed N|warp`, a profile's `input.speed`, 0 = warp; values from 100 are an older profile's percent). At Nx the emulation thread runs N frames for every frame time and waits (and locks to the display) once for all of them; at warp it never waits. `Machine::set_warp(on)` (default: nothing) tells a machine that the frames run from now on are not looked at: it may leave out drawing them, while everything a program can observe stays exact, cycle for cycle (only the framebuffer, and the picture inside a savestate, keeps an older frame). The desktop sets it for every frame of a burst but the last and at warp for all but one a frame time, never with a debugger or the preview attached; such frames are not pushed to the window either. C64 and C128: the VIC-II writes no pixels (`Vic2::set_warp`; with a light pen it does, the pen sees them) — sequencer, sprites, collisions and borders run as always (`machine-c64` test `warp_changes_nothing_but_the_picture`: the same savestate a frame after warp). Amiga: Denise's pixels are not put into the frame (`Custom::set_warp`; Denise itself runs as always, and with a light pen the pixels are written). Atari 8-bit: GTIA draws only the colour clocks with a player or missile on them, for their collisions (`Gtia::set_warp`; off while a light pen points into the picture). `tests/tests/warp.rs` (real ROMs) holds all four to it: the same time, no frame drawn in warp, and the same picture and savestate one frame after; the machine alone then takes 19 % less time a frame on the Atari (5.4 to 4.4 ms) and 4 % less on the Amiga (9.8 to 9.4 ms), the C64 (7.2 to 6.9 ms) and the C128 (8.5 to 8.1 ms) — the rest of the gain is the desktop not converting and pushing unseen frames. Measured 2026-11-17 on the user's PC (release, stub ROM, desktop loop): the C64 reaches 3.6 times real time (2.4 before the VIC-II fast paths and warp), the reference machine 2470 frames a second at warp.
- **Fast paste** (2026-11-17): `Machine::paste_chars(text) -> Option<usize>` (default none) puts the first characters of a text straight into the operating system's keyboard buffer and returns how many it took (0: the buffer still holds earlier ones); `TextFeed::feed` tries it before every frame and falls back to the keys where a machine has no buffer, and after 250 frames in which a buffer took nothing (a program that does not read it). It is no input event, so the session stays with the keys (`TextFeed::pump`) while a recording runs. Buffers are filled only while empty, so a count or pointer the system is just changing is never overwritten; a Commodore count above the buffer's size means no KERNAL keeps its keys there (stub ROM, memory not set up) and the keys type at once. Machines: the Commodore KERNALs' NDX/KEYD (`chips-cbm/src/keybuf.rs`: PET by BASIC version, VIC-20, C64, C16/Plus/4, C128 in both modes, not while its Z80 runs), MSX (KEYBUF with PUTPNT/GETPNT), BBC (MOS buffer 0; the Master's indices a byte lower), Atari (CH, one key a frame), Apple II (the keyboard latch, one key a frame). Measured against the keys with a 40-line listing (`tests/tests/paste_fast.rs`, machine time): BBC 133–138 times faster, MSX 58–63, C64 and VIC-20 24–25, C16/Plus/4 19–20, C128 13 (24 in C64 mode), PET 4032/8032 13–20, PET 2001/3032 3–4 (their editors show a character only in the picture's blank), Atari 4, Apple II 3. Still on keys: CPC, TRS-80, Spectrum, TI-99/4A, KC85, MEGA65.
  - Native protocol: `type {text}` → `{queued, pending, active}` (text goes behind what waits; without `text` only the state), `type_cancel` → `{dropped}`; `"type": true|false` in `capabilities`. The text is typed only while the machine runs. `polydbg type TEXT… | --file FILE | --cancel [--wait]`. Contract test `typed_text`, client test `command_line_client_types_text`, both against the toy machine (its keys land in RAM at `KEYS`).
  - Frontends: desktop Ctrl+V (clipboard through `arboard`; sent when Ctrl is up again, since a held Ctrl would make control codes of the first characters), Ctrl+Shift+V drops the rest, a PASTE button in the console panel; the machine runs at warp while it types. Web: the browser's paste event on the picture and a Paste button, 8 frames a call meanwhile. Headless: `--type TEXT`, `--type-file FILE`, `--type-at FRAME`.
  - Machines (2026-11-15): C64, VIC-20, PET (both keyboards), C16/Plus/4, C128, MEGA65, Atari 8-bit, CPC, TRS-80, Spectrum 128K/+2, Apple II, BBC, MSX, TI-99/4A, KC85 (2026-11-15, its own test); all tried with their ROMs and a short listing (headless). Not offered: ZX81 and Spectrum 48K (a key enters a whole keyword there; a 128K switched to 48 BASIC is not told apart), machines without a keyboard BASIC. Limits: typing is blind (fixed times, no look at the machine), so a machine busy longer than the pause behind RETURN loses keys (seen: the TRS-80's MEMORY SIZE prompt, the first line after choosing TI BASIC); characters without a key are skipped; letters arrive in the machine's default case.
  - Found on the way: the PET business keyboard's table had the main row's digits and the keypad's swapped (also in `mimic-input`'s keymap), so SHIFT+2 gave 2 on an 8032; read from the editor ROM's decode table (bit 7 set = SHIFT leaves the key alone).
- **BASIC debugger** (protocol 11, Phase 35, begun 2026-11-14; see `docs/claude/phases/phase-35-basic-debugger.md`): for machines whose BASIC interpreter the machine describes (`Machine::basic() -> Option<&mut dyn BasicDebug>`, default none; types in `mimic-core::basic`), the debugger works on the BASIC program without knowing the dialect:
  - `basic_info` (dialect, `granularity` = `statement` | `line`, memory space), `basic_state` (`mode` = `inactive` | `direct` | `running`, `line`, `statement`, `addr` = text pointer, `depth` = open GOSUBs), `basic_list {from, to}` (lines with `line`, `addr`, `text` in Unicode, `statements` = offsets of the statements in the text, `raw` as base64; `current` = where the program is), `basic_vars` (name, type `int` | `float` | `string`, address, value; arrays with `dims`), `basic_array {name, first, count}`, `basic_set_var {name, index, value}`, `basic_stack` (frames innermost first: `gosub` with the line and statement of the GOSUB, `for` with variable, limit, step and the FOR's place, `loop` with `word` (`DO`, `REPEAT`, `LOOP`) and the place of the statement that opened a loop without a counter (BASIC 3.5 and later, Simons' BASIC, TSB; added in M2, same protocol version). A procedure call of Simons' BASIC or TSB (`EXEC`) is a `gosub` frame and counts for `depth`; these extensions keep their stacks apart from the CPU stack, so their frames follow the ROM's GOSUB/FOR frames, each kind innermost first. The addresses of lines and variables are in the memory space `basic_info` names: the CPU's view, or the machine's `ram` space where ROMs hide RAM (C16/Plus/4, C128: bank 1 with the variables from `$10000`).
  - Breakpoints: `basic_break_add {line, statement, enabled}` → `{bp}`, `basic_break_remove`, `basic_break_enable`, `basic_break_list`. Their numbers are separate from `break_add`'s. Without `statement` a breakpoint stops when the program enters the line, not when a loop returns into it. **Conditions** (protocol 12): `condition` in `basic_break_add` is an expression over the program's variables in BASIC's own writing — `I = 5 AND A$ <> "END"`, `SC% >= 1000 OR L(3) < 0` (numbers also as `$hex`; `= <> < <= > >=`, `+ - * /`, `AND OR NOT` on truth values; array elements with one index; a variable not set yet is 0 or `""`; names are cut to `name_len` of `basic_info`, 2 in Commodore BASIC). It is checked when set (`condition: …` error; numbers and strings do not mix); what fails only when evaluated (no such array, index outside, division by zero) counts as true. `ignore` lets that many hits with the condition holding pass. `basic_break_condition {bp, condition}` replaces a condition (without `condition`: removes it); `basic_break_list` shows `condition` and `ignore`. Grammar: `mimic-debug/src/basic_expr.rs`. Not to be confused with `break_add`'s conditions over registers and memory (`expr.rs`).
  - Steps, asynchronous like `step_over`: `basic_step {kind}` with `line` (default; into subroutines), `statement`, `over` (the next line at this GOSUB depth) or `out` (until the subroutine has returned), and `basic_run_to {line, statement}`. A run they or a breakpoint end reports `stopped` with the reason `{"kind": "basic_break", "bp", "hits"}` or `{"kind": "basic_step", "step"}` plus `mode`, `line` and `statement`.
  - How it works: the machine names stop points (`BasicDebug::stop_points`: an exec address in the interpreter's dispatch loop or a watchpoint on its "current line" variable). The session arms hidden breakpoints there only while a BASIC breakpoint is enabled or a BASIC step runs, asks `state()` at each hit and resumes silently if nobody waits for it; with nothing active the cost is zero. They never show in `break_list`.
  - Machines so far (2026-11-16): C64, VIC-20, PET (BASIC 1.0, 2, 4.0), C16 and Plus/4 (BASIC 3.5), C128 (BASIC 7.0, and BASIC V2 in its C64 mode) and the Apple II+, IIe and enhanced IIe (Applesoft; its listing is LIST's, with a blank before and behind every keyword: `A = 5: GOSUB 100`; not the original II's Integer BASIC) through `basic_dialects::cbm`; the TRS-80 Model I and III with Level II BASIC and MSX1/MSX2 through `basic_dialects::msz80` (place and stack from the interpreter's SAVTXT and SAVSTK; ELSE and `'` are statements of their own; on MSX the listing writes out the packed constants as LIST does, and the default type double precision has no sign: `A`, `A!`, `A%`, `A$`); the TRS-80 with Level I BASIC through `basic_dialects::level1` (two stop points; the text is the stored line, the blank behind its number included); the ZX81 and the Spectrum 48K, 128K and +2 through `basic_dialects::sinclair` (the statement behind THEN has a number of its own on the Spectrum; the ZX81 has one statement per line; loops are not on a stack there: a FOR variable whose value has not passed its limit is listed as an open loop, behind the GOSUB frames; all numbers are floats, names are reported in upper case with all their characters, `name_len` 0; the listing is LIST's with its blanks around keywords; the Spectrum's stop points are execution breakpoints in its memory space `rom`, which hit only while that ROM is the one paged in — the 128K and +2 have a statement loop in each ROM); the Atari 400/800/XL/XE through `basic_dialects::atari` (every line is tokenised when entered and the listing is LIST's: a blank behind every statement name, blanks around the operators that are words, numbers as the floating point package writes them; what follows THEN is a statement of its own; all numbers are floats; a string takes any length up to its DIM; an array of one dimension and `DIM A(n,0)` look the same; the ROM may be switched off on the XL/XE, then the mode is `inactive`) and the CPC 464, 664 and 6128 through `basic_dialects::locomotive` (Locomotive BASIC 1.0 and 1.1; program and variables are read from the memory space `ram`, which `basic_info` names, since they lie under the lower ROM; the stop point is an execution breakpoint in the new memory space `rom`, which hits only while BASIC is the upper ROM switched in; open WHILE loops are frames of kind `loop`; ELSE and the tick begin statements behind colons the listing hides, what follows THEN runs with the IF; integer, real and string variables, names in upper case, a real one without its `!`; the functions of DEF FN are not listed; a string that is still the constant in the program's text is not written); statement granularity; the gate test is `tests/tests/basic_debug.rs`. The C16/Plus/4 have a memory space `ram` (the RAM behind ROMs and I/O) since then. **BASIC extensions** (M2b): on the C64 a Simons' BASIC or TSB cartridge is recognised while it has the BASIC vectors hooked — `basic_info` then says e.g. `Commodore BASIC V2 + Simons' BASIC`, the listing shows the extension's keywords and statements are counted with its two-byte tokens (`LOOP` is `$64 $3A`). Cartridges only (the user, 2026-11-14); the C64 has a memory space `cartridge` (the cartridge's ROML/ROMH as they would answer now, whatever is mapped) while one is plugged in.
  - `capabilities` has `"basic": true|false`; machines without one answer the `basic_*` commands with an error. `polydbg basic [info | list [FROM [TO]] | vars | array NAME [FIRST [COUNT]] | set NAME|NAME(I) VALUE | stack | break LINE[:STATEMENT] | breaks | unbreak BP | step [statement|line|over|out] | until LINE[:STATEMENT]]`. Contract test `basic_debugger` against the toy BASIC machine `mimic_core::testing::basic::ToyBasic` (no ROM needed).
- Machine-specific extensions are negotiated via `capabilities`; generic clients must work without them.
- Every protocol change needs a contract test and a version bump in the handshake.


## Live preview

- `GET /snapshot.png?machine=<id>[&screen=vic|vdc]` — single frame on demand.
- WebSocket `/preview` — configurable fps (1–50), scale, format (QOI/PNG, delta frames).
- `GET /vectors.json` — a vector display's beam segments of the last frame (as the debugger's `vectors`); 404 for raster machines.
- `GET /controls` — the console's buttons and switches as JSON; the viewer shows them as a panel and sends `{"type": "control", "id", "value"}` back.
- WebSocket `/stream` — raw stream for local viewers (idea from the Ultimate 64 video stream): palette indices at 4/8 bpp or RGB, only changed lines, the pixel aspect ratio for the viewer, no image encoding; optional audio (`audio=1`, 16-bit PCM). Layout in `mimic-preview/src/raw.rs`; the bundled viewer uses it for `filter=raw`.
- On `breakpoint_hit`, attach the current (partial) frame; partial frames mark current raster line/cycle.
- Encoding runs on its own thread from a frame copy; the emulator never waits on the encoder — drop frames under backpressure.
- Optional overlays: raster grid, bad lines, sprite boxes, Atari display-list modes, CPC CRTC changes, Amiga DMA slot map.
- Sprite bounds (2026-11-19): next to the full-size `sprites` boxes, `sprite_bounds` boxes hug the pixels a sprite really set, per use of it (consecutive lines at one column and width): VIC-II (from the 24-bit row the shifter starts with, multicolour as pairs), NES PPU (the fetched pattern planes ORed), S-PPU (the opaque pixels the line renderer draws), TMS9918 and V9938 (the row's pattern bits, magnification counted; a transparent colour sets none). The 2600's `tia_objects` do the same for players, missiles and ball (from what each colour clock drew, read after `Tia::tick`; a second caller of the inlined `outputs()` had cost 9 %, hence `#[inline(always)]` and `cycle::<RECORD>`). The Amiga's `sprites` boxes are tight already (Denise's opaque pixels). Shared helpers: `mimic_core::overlay::{SpriteLine, bound_boxes, row_bounds}`. All record only while switched on.
- The desktop shows the same overlays (2026-11-19): the console panel lists BEAM, RASTER LINES (the preview's `beam` and `grid`; only for machines that place raster lines with `frame_row`) and `Machine::overlays()` as OFF/ON switches (`panel::OVERLAY_BASE`, `Shared::overlay_list`/`overlays_on`). Its wishes join the debugger's and the preview's in one `OverlayWants`, so the machine records the union; `emu::draw_overlays` draws them with `mimic_preview::overlay::OverlaySet` over the RGBA frame of the main screen before the CRT stage (composite: the frame then goes through the RGB path). Frames of another size than the machine's (woven interlace fields, vector phosphor) get none; the snapshot button of the footer saves the raw picture.
