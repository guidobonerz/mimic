# Testing

Part of the project's instructions for Claude Code; the core is `CLAUDE.md` at the repository root, the index of these files is its section "Further documentation".

- CPU cores: Tom Harte SingleStepTests (6502, Z80, 68000), Klaus Dormann 6502 functional test, ZEXALL (Z80), WinUAE `cputester` data (68000).
- C16/Plus/4 TED timing: `tools/ted_timing.py` traces (`trace`, `fine`), raster IRQ entries (`irq`, `irqall`: every line 0–311), the counters $FF1A/$FF1B/$FF1F (`counters`), the CPU clock for every YSCROLL (`yscroll`) and the DMA decision (`dma`: a YSCROLL write starts the DMA of the current line only up to tx 5) equal xplus4 byte for byte since 2026-11-05; `start`/`startdma` (instructions across the switch to single clock at tx 3) 439/440 each. Single clock has no fixed phase (a cycle takes two double clocks, one in the last single double clock); at tx 3 an instruction begun before the line turned is stretched by its cycle count less one double clocks, on a DMA line held to tx 88 + C (`Ted::switch_point`, `Cpu6502::instruction_cycles`); one begun at tx 0 or later runs on (CPU clock per double clock: refresh, single-clock fetch lines, DMA with BA/AEC, line counter turning at $FF1E = $C4, the raster flag seen in the turn's double clock, IRQ pushes waiting during BA as xplus4 has them). Picture test `split` (colour register writes): border pixels match outside the refresh cycles (write shows from the 2nd pixel of the next double clock, 1st pixel old|new), the window is put out 44 pixels after it is composed; open: border writes in the refresh cycles and window writes in single-clock areas (xplus4 puts them elsewhere than the read timing suggests), 27 947 pixels differ. Fetch pipeline since 2026-11-05 (`fetch_pipeline_pictures_match_xplus4`: `rows`, `matrix`, `matrixc`, `fli2`–`fli4` pixel-equal): attributes from the attribute DMA reach the row only when a pointer DMA starts or a field begins, codes only with the pointer DMA, each column keeps the attribute, code and pattern byte it fetched; the character line (`$1F` 0–2) counts on every line from the field's first attribute DMA to line 203 and restarts only with a pointer DMA; the position moves on a row at the end of the attribute DMA line's fetches (its pattern bytes still from the shown row). So $FF14 in the middle of a row changes nothing until the next DMA, and FLI with an attribute DMA forced on every line freezes attributes and codes (xplus4; real Plus/4 FLI's 2-line technique not yet measured). `fli` itself shows uninitialised RAM (power-on patterns differ), no test. Open: `flicnt` (counters under FLI; the program falls behind from line 8, and in those fields $FF1E differs on 49 lines, as before the pipeline).
- C16/Plus/4: VICE `plus4-testlist.in` 12/12 on 2026-11-05 (from 4: debug cartridge at `$FDCF`, "PLUS4 CARTRIDGE " CRTs, open data bus from the TED's last fetch, screenshots compared by a one-to-one colour match, xplus4's picture two lines shorter at the top, the 1551 with its interface cartridge as drive 8 for `Plus4/tcbm`); interactive entries skipped. The 1551 (`drive8=1551`, `drives_cbm::tcbm`) loads, saves and lists the directory with the real DOS (`ted_boot`); the demo Promised Land (Gotu Mega #3, user's D64s) runs with its 1551 fast loader since 2026-11-05 (the TCBM lines are wired both ways: STATUS/ACK driven by the host and read in the drive) and needs a 1551 (with a 1541 it says "MORE THAN 1 DRIVE ON BUS", in xplus4 too); its music is for a SID card at `$FD40` (`sidcard=6581|8580`, built 2026-11-05: Solder's card, clocked at the single clock), without one it is silent; its title picture matches xplus4 to 96 % of the pixels (colour-independent), the rest at raster splits (the open window timing). Multicolour bitmap pair 01 takes a hires 1 dot's colour (matrix bits 4–7, attribute bits 0–2), pair 10 a 0 dot's (matrix bits 0–3, attribute bits 4–6): every pixel of the demo's "Gods of the Universe" picture equals xplus4 (2026-11-05). The TED palette (`ted/palette.rs`) is still an unmeasured approximation, much paler than xplus4 and the real machine (user's photograph of that picture).
- VIC-20: VICE `vic20-testlist.in` 70/72 on 2026-11-05 (from 55: VIA shift register in all eight modes byte for byte against the real VIC-20's `VIC20/via_sr` dumps, T2 reload cycle in the shift modes); 72/72 on 2026-11-08 with a power-on RAM pattern ([S], `machine-vic20::memory::power_on_ram`: $FF in the low 1 KB, the `ops.bin` dump's alternating `00`/`FF` with the phase turning every 8 bytes in $1000-$1FFF, `$00` in expansion RAM; AE reads $0288, Jelly Monsters $1046); open: screenshot entries not compared, interactive and GEO-RAM entries skipped.
- C64 / Commodore 8-bit: Lorenz test suite, VICE test programs (results and trend in `docs/test-results-c64.md`; 2026-11-04: 1173/1240 projected after a full run of 1163 (`C64/` 68/70 and `general/` 323/324 with the power-on RAM pattern, the port's RAM cell and the autostart loading), from `drive/` 45/51 (VIA rules, 1541 address decoding, byte-ready delay) and `VICII/` 229/273 (graphics sequencer: load point, XSCROLL write delay, MCM settling, 6569 g-access mode), last full run 1141 on 2026-11-01; Lorenz 264/264).
- Atari: Acid800, Altirra test programs. CPC: CRTC/Z80 timing test programs. Amiga: vAmigaTS (`vamigats_suite`; 2026-11-01 OCS: 69/537 exact, see `docs/claude/phases/phase-07-amiga-500.md`, vAmigaTS). NES: nestest and blargg's suites (nes-test-roms collection).
- Regression: headless run → N frames → compare against reference images in `tests/reference/` (exact match; update only with an explanation in the commit).
- Test-suite data and ROMs are fetched by `tools/fetch-testdata.sh`, never committed if license forbids.
- Suite runners (Lorenz, Acid800, CPC Acid, VICE test programs, 68020 random tests) record a trend against their previous run with `emu_tests::trend` (`target/tmp/trend/<suite>.txt` + `-history.tsv`): passed before → now, newly passing, newly failing. Report it with every result.
- A new chip or machine feature is not done without tests and savestate round-trip coverage.
- Freezer: tests for each `FreezeMode` (blocked write, frame reapply, banked addresses), cheat-search narrowing on a scripted test program, and freezer-cartridge freeze/restart round trips.
- CRT: CPU-path output is compared against reference images per profile (tolerance-based, not exact); signal-stage tests use known test patterns (color bars, PAL color-mix pairs, Atari artifact stripes). GPU shaders are checked against the CPU path within a tolerance.
- Devices: each `PortDevice` has unit tests at pin level (e.g. 1351 POT values for a given mouse delta); input replay files under `tests/replays/` drive end-to-end tests (load game, replay input, compare frame).
