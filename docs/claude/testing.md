# Testing

Part of the project's instructions for Claude Code; the core is `CLAUDE.md` at the repository root, the index of these files is its section "Further documentation".

- CPU cores: Tom Harte SingleStepTests (6502, Z80, 68000), Klaus Dormann 6502 functional test (also on the 45GS02, `cpu-45gs02/tests/dormann.rs`: passes, 2026-11-11; plus 22 own 45GS02 tests after the MEGA65 guide's descriptions and examples), ZEXALL (Z80), WinUAE `cputester` data (68000).
- C16/Plus/4 TED timing: `tools/ted_timing.py` traces (`trace`, `fine`), raster IRQ entries (`irq`, `irqall`: every line 0–311), the counters $FF1A/$FF1B/$FF1F (`counters`), the CPU clock for every YSCROLL (`yscroll`) and the DMA decision (`dma`: a YSCROLL write starts the DMA of the current line only up to tx 5) equal xplus4 byte for byte since 2026-11-05; `start`/`startdma` (instructions across the switch to single clock at tx 3) 439/440 each. Single clock has no fixed phase (a cycle takes two double clocks, one in the last single double clock); at tx 3 an instruction begun before the line turned is stretched by its cycle count less one double clocks, on a DMA line held to tx 88 + C (`Ted::switch_point`, `Cpu6502::instruction_cycles`); one begun at tx 0 or later runs on (CPU clock per double clock: refresh, single-clock fetch lines, DMA with BA/AEC, line counter turning at $FF1E = $C4, the raster flag seen in the turn's double clock, IRQ pushes waiting during BA as xplus4 has them). Picture test `split` (colour register writes): border pixels match outside the refresh cycles (write shows from the 2nd pixel of the next double clock, 1st pixel old|new), the window is put out 44 pixels after it is composed; open: border writes in the refresh cycles and window writes in single-clock areas (xplus4 puts them elsewhere than the read timing suggests), 27 947 pixels differ. Fetch pipeline since 2026-11-05 (`fetch_pipeline_pictures_match_xplus4`: `rows`, `matrix`, `matrixc`, `fli2`–`fli4` and, since 2026-11-08, `fli2line` pixel-equal; `fli2line` is the real two-line FLI, YSCROLL and $FF14 every second line: each pair of lines gets codes and attributes of its own matrix and the character line runs 0–7 straight on, so only the field's first pointer DMA sets it to 0): attributes from the attribute DMA reach the row only when a pointer DMA starts or a field begins, codes only with the pointer DMA, each column keeps the attribute, code and pattern byte it fetched; the character line (`$1F` 0–2) counts on every line from the field's first attribute DMA to line 203 and restarts only with a pointer DMA; the position moves on a row at the end of the attribute DMA line's fetches (its pattern bytes still from the shown row). So $FF14 in the middle of a row changes nothing until the next DMA, and FLI with an attribute DMA forced on every line freezes attributes and codes (xplus4; real Plus/4 FLI's 2-line technique not yet measured). `fli` itself shows uninitialised RAM (power-on patterns differ), no test. Open: `flicnt` (counters under FLI; the program falls behind from line 8, and in those fields $FF1E differs on 49 lines, as before the pipeline).

- C128: VICE `c128-testlist.in` 1930/2015 without the 135 ZEXALL parts (`EMU_VICE_SKIP=zex128`; they run up to 1.2 billion cycles each) on 2026-11-09, from 1912 in the first run: debug register at `$D7FF` (also written by the Z80 through its I/O space: the runner checks the register after every frame), "C128 CARTRIDGE" CRTs as the external function ROM (`devices_cartridge::c128`, `ExpansionCart::peek_function`), C64 mode keeps the MMU's RAM bank and shared RAM and maps relocation target pages back to page 0/1 without moving pages 0/1 (`Mmu::ram_c64`, `c128/c64modemmu`, confirmed on real hardware there), P0H/P1H latched until P0L/P1L, no register mirror in `$D50C-$D5FF`; the Z80 timing tests 1865/1871. 2026-11-09 later: 1934 with the 2 MHz picture (`c128/2mhzVIC` 4/4): in 2 MHz mode the VIC-IIe's g-access latches the byte of the 8502's phi1 access and its c-access reads $FF with the colour from the low nibble of the phi2 access, BA does not stop the 8502, the refresh cycles 11-15 and the first cycle after the switch give it only phi2 (121 cycles per PAL line), an I/O access (not the MMU) in phi1 is stretched over the cycle; the TEST bit ($D030 bit 1) steps the raster counter every cycle, through 312 before it wraps, and the picture rows are counted like a monitor (`Vic2::out_line`: lines below a cut move up). Then 1940 projected (`c128/` run: 1923 → 1929, none newly failing) with the MMU rules of `c128/mmu/mmuswap-*` (`mmu/` 30/30, `c64modemmu-10`): shared RAM is decided by the address the CPU puts out, not the relocated one, and with P0 and P1 on one page that page reads the stack page. `c128/d030tester` 0/33 still: its values (lines cut, cycles lost, raster, frame length) match, but 11 references show VICE's PAL hue shift after an odd number of cut lines (a colour outside the palette, not reachable in an indexed frame), the rest differ in the top two rows and in the bad line left in 2 MHz mode. Then about 1972 projected (`c128/` run 1958 → 1961 with the last fixes, none newly failing; `c64modemmu` 51/51, `mmu` 30/30, `z80` 1871/1871): the Z80's view of memory and I/O (`Memory::z80_access`: in bank 0 `$0000-$0FFF` moved to `$D000-$DFFF` — BIOS for memory reads, RAM for writes and I/O reads; the colour RAM at `$1000-$13FF` while the CR shows I/O; I/O cycles reach the chips at `$D000-$DFFF` whatever the CR or the C64 map say, MMU reads only with I/O on, MMU writes always; other I/O reads see RAM through the MMU, `$FF00-$FF04` in both kinds; C64 mode uses the C64 map, memory reads at I/O addresses see RAM, writes the chips), C64 mode keeps colour RAM bank 1 for CPU, VIC and Z80, its page relocation maps accesses to a target page back even when that is page 0 or 1, and RCR bits 4-5 read 0 (`z80/outi`). Then 1976/2015 in a full run (2026-11-09, none newly failing): a write to $00/$01 gives the RAM cell the MMU maps it to the data bus's byte (`ram0001`, `ram0001mmu` bank test), the VIC keeps the RCR's bank in C64 mode (`vic-mmu`), the runner puts D64 entries into a 1541 (`burstmode`). `c128/d030tester` is deferred (its values match; the pictures differ in VICE's PAL hue shift and rendering details). - Regression: headless run → N frames → compare against reference images in `tests/reference/` (exact match; update only with an explanation in the commit).
- Test-suite data and ROMs are fetched by `tools/fetch-testdata.sh`, never committed if license forbids.
- Suite runners (Lorenz, Acid800, CPC Acid, VICE test programs, 68020 random tests) record a trend against their previous run with `emu_tests::trend` (`target/tmp/trend/<suite>.txt` + `-history.tsv`): passed before → now, newly passing, newly failing. Report it with every result.
- A new chip or machine feature is not done without tests and savestate round-trip coverage.
- Freezer: tests for each `FreezeMode` (blocked write, frame reapply, banked addresses), cheat-search narrowing on a scripted test program, and freezer-cartridge freeze/restart round trips.
- CRT: CPU-path output is compared against reference images per profile (tolerance-based, not exact); signal-stage tests use known test patterns (color bars, PAL color-mix pairs, Atari artifact stripes). GPU shaders are checked against the CPU path within a tolerance.
- Devices: each `PortDevice` has unit tests at pin level (e.g. 1351 POT values for a given mouse delta); input replay files under `tests/replays/` drive end-to-end tests (load game, replay input, compare frame).
